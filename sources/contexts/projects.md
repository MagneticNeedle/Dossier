# BFPORTAL.GG

When DICE/Ripple Effect shipped Battlefield Portal in 2021, they gave players a powerful in-game mode editor but no way to share what they built outside the game itself — creators had nothing but raw share-codes and scattered Discord posts. I designed and built bfportal.gg to close that gap: a full-stack platform (Python/Django on Wagtail CMS, Tailwind, Dockerised, Discord OAuth, with an auto-fill submission API integrated against gametools.network) where the community could publish, search, categorise, and discover custom experiences.
Four-plus years on, the platform has grown to 17,000+ registered users and a 7,000-member Discord, is fully community-funded via Patreon (no commercial backing or VC), and operates under EA's official Fansite Agreement. What started as a single repo has snowballed into a 20-repo open-source ecosystem under the battlefield-portal-community GitHub org — including an unofficial PortalSDK, scripting examples and templates in TypeScript, a UI builder for Battlefield 6 custom interfaces, automated documentation tooling, and a service-tracker. The main repo alone has 670+ commits across seven releases, and the platform successfully carried its userbase through the Battlefield 2042 → Battlefield 6 transition. I built and shipped the original product, run the infrastructure, and lead a team of volunteer contributors and moderators who keep it alive.
To me, the strongest signal isn't the codebase itself — it's that a community of thousands chose to fund and depend on something I built, when no one was paying me to make it.

# GAMETOOLS.NETWORK

gametools.network is a community-run platform for Battlefield server admins and players — public stats APIs, server administration tools, Discord bots, and live dashboards across BF2 through BF6.
The whole project exists because EA/DICE does not publish a public API for any of the Battlefield titles. Every endpoint the platform uses had to be discovered by reverse-engineering the game and web clients: dumping the game's binary and JavaScript bundles to find the routes it talks to, intercepting the gRPC-Web/protobuf traffic between the client and DICE's gateway, and reconstructing the message schemas from the wire format until they could be expressed as .proto files and typed clients. Without that foundation, none of the stats lookups, server management actions, or Portal queries below would be possible. It also means the project lives with the constant cost of EA rotating endpoints, schemas, and tenancy headers without notice — keeping the protocol layer current is ongoing work, not a one-off.
I contributed to three backend services on top of that foundation.
origin-public-api — the public read API
Why it was needed. The website, third-party Discord bots, and embedded widgets all need fast, cacheable access to player stats, server lists, and platoon data across multiple Battlefield titles. Hitting the reverse-engineered DICE endpoints directly for every request would be slow, rate-limited, and would get the project's IP space banned. We needed a layer that aggregates upstream data, normalises it across game generations, and serves the bulk of traffic from cache.
What we built. A horizontally scaled API (the "Instances of" tier in the system diagram) fronted by Cloudflare and an Envoy load balancer. It uses Redis for hot in-memory data and MongoDB for persisted state, and explicitly signals Cloudflare to cache responses so most public read traffic never reaches origin. For endpoints that require live data — current players in a server, recent matches — the public API calls into our internal gateway-rest-api rather than DICE directly, keeping all upstream traffic on a single chokepoint that handles auth, retries, and backoff in one place. When EA changes a field or rotates an endpoint, only the gateway has to adapt.
operations-api — the Manager backend
Why it was needed. Rented Battlefield servers expose only limited admin controls through EA's in-game web UI. Community admins running large competitive or public servers need bulk ban management, cross-server ban sync (vBan), scheduled rules, automated kick logic, live scoreboard and chat-log capture, and audit trails — none of which EA provides. Everything has to be built on top of the same reverse-engineered DICE endpoints the game client itself uses, including the privileged admin RPCs that aren't exposed in any public form.
What we built. A Flask backend at manager-api.gametools.network that backs the React Manager frontend. It stores group, server, and admin state in MongoDB and coordinates a worker fleet via RabbitMQ: a Rust task scheduler enqueues recurring jobs, workers execute them by going through the gateway-bf1 PlayerInfo API to fetch live state from DICE, and the results — scoreboards, logs, ban deltas — get written back to Mongo. Decoupling the workers from HTTP request lifetimes means the API stays responsive even when DICE is slow or returning errors, which is frequent given we're using endpoints they don't officially support.
bfportal-grpc-bf6 — typed client for the BF6 Portal gRPC API
Why it was needed. Battlefield 6's Portal (the in-game custom-experience platform) moved to gRPC-Web for its web frontend. To use it from anything other than the official site, we had to capture the gRPC-Web traffic from portal.battlefield.com, recover the protobuf message definitions from the wire format and the JS bundles, and reproduce the session/auth handshake the browser performs. Every project across the org that wanted to read BF6 Portal data — Playground definitions, experience metadata, reporting — would otherwise have to redo that same reverse-engineering work and maintain its own stubs. The README states the goal plainly: keep one repo in sync with the protocol so the rest can just bump a package.
What we built. A shared library published to both npm and PyPI, with reconstructed .proto files (authentication, localization, play, reporting) as the source of truth and codegen pipelines for both ecosystems. The library handles the full request path: pulling a gateway session from a user's sid/remid cookies, exchanging it for a web access token, attaching the right x-dice-tenancy / x-gateway-session-id / x-grpc-web metadata, and encoding/decoding length-prefixed gRPC-Web frames over HTTP/2. Consumers import a typed client and call methods like getPlayElement directly without knowing any of that exists.
